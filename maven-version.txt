# 1️⃣ How Maven Versioning Normally Works
gitgithub
In standard Maven practice:

* Every artifact has a version in its `pom.xml`
* Version is changed using:

  ```bash
  mvn versions:set -DnewVersion=1.2.0
  ```
* Releases are typically handled by:

  ```bash
  mvn release:prepare
  mvn release:perform
  ```

The **POM is the single source of truth** for versioning.

That has been the Maven philosophy since day one.

---

# 2️⃣ What SNAPSHOT Actually Means (Very Important)

If you have:

```
1.3.0-SNAPSHOT
```

This means:

* It is mutable
* Every build publishes a new timestamped artifact to Nexus
* Other projects pulling it will always get the latest snapshot

In Nexus, it becomes:

```
1.3.0-20260304.101233-4
```

Snapshots are for:

* Active development
* Inter-service integration during development

Releases are:

```
1.3.0
```

They are immutable and safe for production.

### Best practice in microservices:

* `main` branch → SNAPSHOT
* Release branch or tag → Release version
* Only releases deployed to production

# 3️⃣ Parent + BOM Structure

You described:

```
Parent POM
   imports BOM
      defines versions
Microservices reference Parent
```

This is correct and modern.

Version flow looks like:

```
Parent version
    ↓
BOM version
    ↓
Dependency versions
```

Important:

Each microservice still has its own `<version>`.

Even with a parent, the microservice artifact must have a version.

# 4️⃣ The DevOps Proposal: Version in Separate File / Env Var

This approach usually means:

* Version stored in something like:

  * `version.txt`
  * GitLab CI variable
  * YAML file
* Pipeline injects version into Maven during build:

  ```bash
  mvn versions:set -DnewVersion=$CI_VERSION
  ```

This is common in:

* Large enterprises
* GitOps-heavy environments
* Container-first deployments
* Strict CI/CD governance

BUT…

It is not Maven’s native model.

It is CI-driven versioning.

---

# 5️⃣ Why They Might Want That

DevOps is likely optimizing for:

### 🔹 1. Immutable CI pipelines

Version bump happens in pipeline, not by developers.

### 🔹 2. Centralized release control

Prevents rogue version changes.

### 🔹 3. Git tag driven releases

Example:

```
git tag v1.4.0
```

Pipeline:

* Extracts tag
* Sets Maven version
* Builds
* Publishes to Nexus

### 🔹 4. Docker alignment

Often Docker image tag = Maven version.

# 6️⃣ Do You *Need* That?

Short answer:

👉 No, not strictly.

Maven already solves versioning cleanly inside the POM.

What matters is:

* Who controls releases?
* How automated do you want it?
* Are microservices independently released?

# 7️⃣ Recommended Strategy for Microservices (Clean + Modern)

Here’s what I recommend for your architecture:

---

## 🔹 A. Each Microservice Owns Its Version

In each microservice:

```xml
<version>1.0.0-SNAPSHOT</version>
```

During development → snapshot.

---

## 🔹 B. Use Git Tags for Releases

When ready:

```bash
git tag 1.0.0
git push --tags
```

Pipeline:

1. Detect tag
2. Run:

   ```bash
   mvn versions:set -DnewVersion=${CI_COMMIT_TAG}
   ```
3. Deploy to Nexus (release repo)

---

## 🔹 C. Use SNAPSHOT for Inter-Service Dev

Shared library:

```
common-lib: 1.2.0-SNAPSHOT
```

Services consume snapshot during dev.

When stable:

```
common-lib: 1.2.0
```

Services upgrade intentionally.

This avoids hidden breaking changes.

---

## 🔹 D. BOM Strategy

Only the BOM controls dependency versions.

Microservices:

```xml
<dependencyManagement>
    <dependency>
        <groupId>com.myorg</groupId>
        <artifactId>platform-bom</artifactId>
        <version>2.1.0</version>
        <type>pom</type>
        <scope>import</scope>
    </dependency>
</dependencyManagement>
```

When shared libs change → release new BOM version.

Microservices opt into upgrade.

That is clean version governance.

# 8️⃣ What I Would Avoid

❌ Manually editing version files in multiple places
❌ Forcing developers to increment versions by hand in YAML
❌ Tightly coupling GitLab YAML and Maven model
❌ Automatic silent version bumps

Those approaches often create more operational confusion.

# 9️⃣ Snapshot vs Release — Simple Rule

| State | Version          | Nexus Repo |
| ----- | ---------------- | ---------- |
| Dev   | `1.2.0-SNAPSHOT` | snapshots  |
| QA    | `1.2.0-RC1`      | releases   |
| Prod  | `1.2.0`          | releases   |

Keep it simple.

> 📌 The POM is the source of truth.

> 📌 SNAPSHOT for development.
> 📌 Immutable releases in Nexus.
