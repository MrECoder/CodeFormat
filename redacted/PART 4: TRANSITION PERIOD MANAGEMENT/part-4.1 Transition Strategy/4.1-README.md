4.1 Transition Strategy (Recommended Approach)
Phase 1: Preparation (Week 1)

Communication

Announce migration to development team
Share documentation (this guide)
Schedule knowledge transfer session


Environment Setup

Configure Nexus repositories (Part 3)
Set up test environment
Update CI/CD templates


Initial Testing

Test migration on a single non-critical component
Validate build pipeline with new versioning
Confirm Nexus artifact deployment



Phase 2: Parent POM Migration (Week 2)

Migrate parent-pom repository:

bash   cd parent-pom-repo
   git checkout -b feature/ci-friendly-versions
   
   # Update all 4 POMs (bom, parent, aggregator, code-style)
   # Use provided complete POMs from Part 1
   
   # Test locally
   mvn clean install -Drevision=0.0.1 -Dchangelist=-SNAPSHOT
   
   # Commit and push
   git add bom/pom.xml parent/pom.xml aggregator/pom.xml code-style/pom.xml
   git commit -m "Migrate to CI-friendly versions"
   git push origin feature/ci-friendly-versions

Create and merge MR:

Create Merge Request in GitLab
Run CI/CD pipeline
Verify artifacts deployed to Nexus
Merge to main after approval


Deploy parent POMs:

bash   # After merge to main
   mvn clean deploy -Drevision=0.0.1 -Dchangelist=-SNAPSHOT
Phase 3: Component Migration (Week 2-3)
Migrate components in dependency order:

common-java-components (no internal dependencies)
common-rabbitmq-components (depends on common-java-components)
common-notification-service (depends on common-java-components)

For each component:
bashcd common-java-components
git checkout -b feature/ci-friendly-versions

# Update POM (use template from Part 1.5)
# Key changes:
# - Parent version: ${revision}${changelist}
# - Remove artifact version tag
# - Add revision/changelist properties
# - Remove version from internal dependencies
# - Add flatten plugin

# Test
mvn clean install -Drevision=0.0.1 -Dchangelist=-SNAPSHOT

# Commit, MR, merge
git add pom.xml
git commit -m "Migrate to CI-friendly versions"
git push origin feature/ci-friendly-versions
